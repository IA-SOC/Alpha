# Persistence and performance

> [!warning] Proposal, not tested in Sprint 2
> The snippets below were not run against the Sprint 2 code. Option A is copied from the previous version, where it was implemented and measured. Check package names in their documentation before using them.

## Persistence: keep pending reviews across restarts

**Today:**

| Data | Where | Survives restart? |
| --- | --- | --- |
| Accepted case | SQLite `cases` | Yes |
| Last investigation result | SQLite `investigations` | Yes |
| Review checkpoint (paused graph) | `InMemorySaver` in `InvestigationService.sessions` | **No** |
| Per-case lock | `InvestigationService.locks` | No |

After a restart, `GET /investigation` still works, but `POST /review` returns `409` until the case is investigated again.

**Proposal:** a SQLite checkpointer (or Postgres for several instances).

```powershell
python -m pip install langgraph-checkpoint-sqlite
```

In `app/services/investigation_service.py`:

```python
from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver

class InvestigationService:
    async def _graph(self):
        if self._saver is None:   # open once, close on app shutdown
            self._saver = await self._stack.enter_async_context(
                AsyncSqliteSaver.from_conn_string("data/checkpoints.sqlite3"))
        return build_graph(checkpointer=self._saver)
```

Then:

- In `run`, use `await self._graph()` instead of `build_graph()`.
- In `review`, instead of reading `self.sessions`, read `run_id` from the saved investigation (`self.store.get_investigation(case_id)["run_id"]`) and rebuild the graph with the same saver.
- Add `data/checkpoints.sqlite3` to `.gitignore`.
- `build_graph()` already accepts a `checkpointer`, so the graph itself does not change.

Even with this, per-case locks stay in memory: keep **one worker**, or move locking into the database.

## Performance

Measured flow today: about 1.6 to 3.3 s from intake to `pending_review` for 4 alerts (see [[09 Tests and synthetic cases#The real HTTP demo]]). The fixed cost is the three MCP servers: `call_tool` starts a **new subprocess per call**, one after another, and each takes about 0.9 s to load the `mcp` library.

### Option A: start the servers in parallel, once per case · from the previous version

The previous version measured this on `bruteforce_wazuh.json`: from about 4.5 s to about 3.0 s per case, and phases 2 and 3 went from about 2.8 s to about 17 ms. To port it to `agent/graph.py`:

```python
from contextlib import asynccontextmanager
from contextvars import ContextVar

_SESSIONS: ContextVar[Optional[Dict[str, Any]]] = ContextVar("mcp_sessions", default=None)


@asynccontextmanager
async def mcp_sessions():
    """Start the three servers at once; starting them one by one was the slowest part."""
    async with AsyncExitStack() as stack:
        sessions = {name: await McpToolClient(SERVERS[name]).open(stack)
                    for name in ("mitre", "hypothesis", "timeline")}
        await asyncio.gather(*(s.initialize() for s in sessions.values()))
        token = _SESSIONS.set(sessions)
        try:
            yield
        finally:
            _SESSIONS.reset(token)


async def call_tool(server, tool, arguments):
    sessions = _SESSIONS.get()
    if sessions:
        return await call_session_tool(sessions[server], tool, arguments)
    async with AsyncExitStack() as stack:
        return await McpToolClient(SERVERS[server]).call(stack, tool, arguments)
```

And in `investigate()`:

```python
    async with mcp_sessions():
        await app.ainvoke({"case": case, "audit_log": []}, config)
```

This also needs `McpToolClient.open()` and `call_session_tool()` in `orchestrator/client.py`, copied from the previous version. Sessions travel in a `ContextVar`, outside the LangGraph state, which must stay serializable.

### Option B: MCP servers over HTTP

Run the servers as permanent services (FastMCP streamable HTTP transport) and connect to them. This removes the start-up cost per case and fits the container deployment the brief asks for. `core/logic.py` does not change. Because the agent now runs inside FastAPI, this can also be done by opening the sessions once in the app `lifespan`.

### Option C: call `core/logic.py` directly

The fastest option, but it loses the MCP separation. Only for local tests.

### Small win: skip the discarded analysis

`investigar_hipotesis` runs `build_attack_analysis` on all alerts and then, with the adapter, replaces the result with `correlated_attack_analysis`. Moving the first call into an `else` saves work. It is cheap today, but it would matter with an LLM.

## Measure before and after

The `audit_log` already has each phase's duration:

```python
state = asyncio.run(investigate(case, thread_id="perf"))
for e in state["audit_log"]:
    print(e["node"], e["duration_ms"], "ms")
```

For the brief's requirement (50 alerts in under 5 minutes), build a 50-alert contract case and record the median (p50) and 95th percentile (p95) of several full runs through the API. This has **not** been done in Sprint 2.
