# Sequence correlations

**Goal:** detect patterns that depend on the **order** of alerts, not on one alert alone. The example: a successful login preceded by failures for the same user and host, which suggests the brute force worked (T1078 Valid Accounts).
**File:** `core/logic.py`

> [!info] Not the same as the correlation engine
> The Sprint 2 [[16 Correlation engine]] answers "do these alerts observe the same activity?" using shared entities. It does not say anything about order or technique. This guide adds **technique-level** sequence detection on top of it.

> [!example] Tested in the previous version
> With this function, the agent detects T1078 in the Wazuh case (alerts `…1001` to `…1004`) and the scaffold case (`a1`, `a2`), with no false positive in the phishing case. `core/logic.py` has the same rules and functions in both versions (only comments differ).

## 1. Add the function

In `core/logic.py`, below `map_alerts_to_mitre`:

```python
from datetime import datetime, timedelta

FAILURE_SIGNALS = ("failed_login", "brute_force", "multiple_auth_failures")


def _is_failure(alert):
    return any(p in s for p in FAILURE_SIGNALS for s in _alert_signals(alert))


def _is_success_login(alert):
    text = " ".join(_alert_signals(alert))
    return "success" in text and ("login" in text or "authentication" in text)


def detect_success_after_failures(alerts, window_minutes=30):
    """Successful login preceded by failures for the same user and host -> candidate T1078."""
    def when(a):
        return datetime.fromisoformat(a["timestamp"].replace("Z", "+00:00"))

    mappings = []
    for ok in (a for a in alerts if _is_success_login(a) and a.get("timestamp")):
        failures = [
            f for f in alerts
            if _is_failure(f) and f.get("timestamp")
            and f.get("user") == ok.get("user") and f.get("host") == ok.get("host")
            and timedelta(0) <= when(ok) - when(f) <= timedelta(minutes=window_minutes)
        ]
        if failures:
            mappings.append({
                "technique_id": "T1078",
                "technique_name": "Valid Accounts",
                "tactic": "Initial Access",
                "supporting_alert_ids": [f["id"] for f in failures] + [ok["id"]],
                "confidence": 0.6,
            })
    return mappings
```

The output has the same shape as `map_alerts_to_mitre`, so the rest of the agent handles it unchanged. With the API, phase 2 then cuts the mapping to each correlation group, so failures and success must also be `related` (same group) to support one hypothesis.

## 2. Wire it in

At the end of `map_alerts_to_mitre`, before the `return`:

```python
    mappings += detect_success_after_failures(alerts)
    return sorted(mappings, key=lambda m: m["confidence"], reverse=True)
```

> [!warning] Times without a zone
> `when()` needs times with a zone. Through the API, alerts without a valid UTC time arrive with an empty `timestamp`, so the `a.get("timestamp")` guard skips them. Through the CLI, a time without a zone arrives as its original text (for example `2026-09-18 09:30:00`), and subtracting it from a UTC time raises a `TypeError`. If such cases are possible, keep only times ending in `Z` (`a.get("timestamp", "").endswith("Z")`).
