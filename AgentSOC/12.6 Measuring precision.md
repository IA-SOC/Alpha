# Measuring precision

**Goal:** know how often the agent is right, with defensible numbers, and compare improvements (new rules, LLM) against a baseline.

> [!important] There is no measurement today
> The "8 of 19" coverage is a count against references we wrote ourselves. It shows where the catalog fails; it is not precision. There is also no basis for "99%". The client brief sets no percentage; that number came up in team discussion. Sprint 2 tests establish **behavior**, not real-world precision or recall.

The full method is in the skill's `references/protocolo.md`, section *Medición de precisión*. Practical summary:

## 1. Build the set

- **Cases from the four families** in the brief: phishing and credential theft, brute force with lateral movement, exfiltration, pre-ransomware activity.
- **Negative and hard cases:** benign, ambiguous, missing data, adversarial text.
- **Real formats** (anonymized ECS and Wazuh exports) when the client provides them, in contract v1.0.

## 2. Label

For each case, an analyst (ideally two, with a tie-breaker) records:

- the correct techniques;
- acceptable alternatives (for example T1021 instead of T1021.002);
- **which alert pairs are really related** (new: this lets you measure the correlation engine too);
- whether the case cannot be mapped;
- what evidence is missing.

Store labels **in a separate file**, never inside the case, so they cannot leak into the analysis. The intake contract would reject them anyway as unknown envelope fields, and submitted correlation labels are never used as evidence.

## 3. Split

| Set | Use |
| --- | --- |
| **Development** | May be looked at to write rules or prompts |
| **Test** | Only for measuring. Nobody looks at it while developing. |

If someone uses a test case to tune something, that case moves to development.

## 4. Measure

| Metric | Question it answers |
| --- | --- |
| Precision per technique | Of what the agent proposes, how much is right? |
| Recall per technique | Of what had to be found, how much was found? |
| F1 (micro and macro) | Balance between the two |
| False positives on benign cases | Does it invent incidents? |
| Abstention rate | How often does it say `insuficiente`? |
| **Pair classification accuracy** (new) | Does `related`/`unrelated` match the analyst's labels? |
| **Noise precision** (new) | Are noise candidates really unrelated? |
| Reference accuracy | Do the cited alerts really support the claim? |
| Supported actions | Does each action follow from a finding? |

Always report **n** (number of cases), the confidence interval and the versions of rules, correlation profile (`entity-time-v1`, window), prompt, model and dataset.

> [!note] How many cases are needed
> To claim with 95% confidence that the error is below 1%, you need at least about 300 independent predictions with no error. Four cases, one per family, are smoke tests, not evidence of precision.

## 5. Compare

Run the same test set with each variant (current rules, expanded rules, rules + LLM, different correlation windows) and compare the metrics. An improvement on development that does not repeat on test is overfitting.
